# Research protocol — data, field mapping, method and scope

Phase 5A establishes the data protocols that tie a **software revision**, a **formal model**, its **validation
material** and the **model–program conformance** results together, so that from one conclusion you can reach the
model, the program version, the observation and the test. 5B–7 extend this document in place.

Two experiment lines are counted apart throughout phases 5–7:

| Track | Meaning |
|---|---|
| `implementation_conformance` | software model verification with its real purpose kept, never disguised |
| `synthetic_representation` | fixed, human-reviewed synthetic problems (representation study); **not opened in 5A** |

## Protocols

| Protocol | Source | JSON Schema |
|---|---|---|
| `fal-research-case/v1` | `formal_lab_contracts.research.ResearchCase` | `contracts/research/fal-research-case-v1.schema.json` |
| `fal-conformance-result/v1` | `formal_lab_contracts.research.ConformanceResult` | `contracts/research/fal-conformance-result-v1.schema.json` |

The schemas are regenerated by `python -m formal_lab_contracts.research --out contracts/research` (part of
`make contracts`, so `make contracts-check` covers them). They reference formal-lab-contracts/v2's `ModelRef`,
`ArtifactRef` and `Digest` but are **independently versioned**: they are not in the v2 object set, so the frozen v1
contract and the v2 digest are untouched. v1 stays frozen; v2 is incremental and compatible; old replay bundles stay
readable.

### Three separately versioned identities

A software version, a model version and (from phase 6) a provider model are three different identities, recorded
apart. The commit before a fix is **not** automatically the valid defect baseline; the protocol holds the real build
premises and any relevant revisions, which 5B verifies.

## `fal-research-case/v1` — the fields it must express

| Field group | What it carries |
|---|---|
| `identity` | `case_id`, `case_version`, `track`, `mechanism_family`, readable `title` and `purpose` (kept, never disguised) |
| `software` | repository, license, real `revision` + `trees` (`git rev-parse <rev>:<path>`), config digest, build/runtime deps; `variant` marks an own test variant — it does not pose as an upstream release |
| `comparison` | `before`/`after` each with its revision or artifacts and `change_basis`; a missing side states why; `regression_test_source` |
| `models[]` | `ModelRef`, `semantic_profile`, each property's id + **expr digest**, input/step `bounds`, `assumptions` and `uncovered_semantics` |
| `correspondence[]` | program component → model state/action/observation, with the relation typed `MANUAL_REVIEW` \| `MEASURED` \| `FORMAL_PROOF` |
| `validation` | `ArtifactRef`s for fixtures, observations, model checks, regression and conformance; **reference answers kept apart** from `task_input`s |
| `reproduction` | local entry point, reset/cleanup, seeds / external nondeterminism, the commands actually run, prerequisites |
| `artifacts[]` | every file by `path` + `sha256` + `role`; identity is the digest, never the file name |

Identity is by digest, never by name: an artifact by `sha256`, a model by its package digest, a property by the digest
of its canonical `{id, kind, expr}`, a software version by its commit and the git tree ids of the relevant paths. A
file existing only proves the material exists.

### Import validation (what is rejected)

`validate_case(files, repo=None)` checks, and import rejects, at least: a changed case whose `case_digest` was not
updated (`CASE_DIGEST_MISMATCH`); a missing or altered artifact (`ARTIFACT_MISSING` / `ARTIFACT_DIGEST_MISMATCH`); a
property id / expression-digest disagreement (`PROPERTY_DIGEST_MISMATCH`, `PROPERTY_UNKNOWN`); a model-ref or digest
disagreement (`MODEL_REF_MISMATCH`, `MODEL_DIGEST_MISMATCH`); a before/after side mix-up (`SIDE_MISMATCH`,
`VERSION_MISMATCH`); a reference answer listed (or byte-identical) as a task input (`REFERENCE_IN_TASK_INPUT`); a
conformance result bound to another definition, software or observation (`STALE_CONFORMANCE`, `CASE_MISMATCH`), or a
decisive correspondence with no observation (`MISSING_OBSERVATION`). With a repository, the software revision and tree
digests are recomputed (`REVISION_UNKNOWN`, `TREE_DIGEST_MISMATCH`); without one, that is a warning
(`SOFTWARE_NOT_VERIFIED_HERE`), not a pass.

## `fal-conformance-result/v1` — three layers kept apart

A single result records, **apart from each other**:

1. **model conclusion** — the model-internal check verdict (`ModelVerdict`: the platform's `SearchVerdict`, plus
   `TIMEOUT` and `NOT_RUN`), with the query and the model-check artifact;
2. **program regression** — the program's own regression-test result (`PASS` / `FAIL` / `NOT_RUN` / `UNKNOWN`);
3. **correspondence** — whether the two agree within a declared `scope` (`CorrespondenceStatus`).

A single passing regression never becomes a full semantic-equivalence proof. `UNKNOWN`, `TIMEOUT`, `UNSUPPORTED` and
`NOT_COMPARABLE` observations stay independent states. A model counterexample is `UNCONFIRMED` until the program shows
it, and `SPURIOUS` only with evidence it comes from an abstraction error. The `scope` text always denies that agreement
on the observed steps is semantic equivalence.

### Field mapping — how a conclusion reaches the evidence

`replay_conformance` replays the recorded program observations on a model the way the engine compares effects
(`belief(obs) → predict(state, action) → compare_effects`) and emits `items[]` (step, action, element, predicted,
observed, status). The result references the `case` (by `definition_digest`, since results are case artifacts
themselves), the `model` (`ModelRef`), the `software` (revision + trees), the `property_id` + `property_digest`, the
`bound`, the `program_observations` (by artifact id + sha), and the tool identities. So one `correspondence` verdict
locates: the model (ModelRef / artifact), the program version (software revision + trees), the observation (artifact
id + sha, and on the platform the imported run) and the test (regression / model-check artifacts).

## Method and scope

The approach is **independent program observation checking the abstract conclusion** — see *Formal Verification at
Higher Levels of Abstraction* (<https://www.kroening.com/papers/iccad2007.pdf>). This repository uses that wording
accurately for empirical conformance; a formal abstraction-preservation proof is separate and not claimed. 5A uses the
existing Z3 verifier and the local order service only; CBMC is a 5B per-language conditional, not a 5A prerequisite.

Phase 6 provider-model inference runs over an online API and is counted apart from the developer (coding) models. Phase
6 chooses task inputs explicitly (`task_input` artifacts: model + property + fixture, no answers); the full case is
never handed to a model, and there is no cross-domain disguise or reverse-execution conversion.

## Ordinary business case (5A acceptance)

`research/cases/orders-p2-speed/` — the order service's processing-speed model/reality deviation, built and validated
by `scripts/p5a_orders_case.py`:

- **program**: `examples/local-order-service` at HEAD, run under the lab `deviation` operating condition (station p2 at
  half speed) — an `own_test_variant`, not an upstream release;
- **models**: `v1` belief (nominal speed) and `v2` revised (`slow[p2]=true`), property `all_completed` (goal);
- **observation**: a replay bundle of one real rule-driven run against the service process;
- **result**: against the same recorded run the belief model **DEVIATES** (first difference at a recorded step) and the
  revised model **CORRESPONDS**; the program regression PASSes; the bounded model conclusion is recorded as-is.

This case validates the **generic** protocol only; 5B provides domain properties.

## Implementation-level case (5B): tenant/object access isolation

`research/cases/orders-tenant-isolation/` — a software **safety** property (tenant isolation) made observable on the
real order service, built and validated by `scripts/p5b_isolation_case.py`. Defensive software verification on local
test tenants; the oracle reads real HTTP results and real stored state (through each tenant's own authorized
principal), never a self-reported success.

- **Software under study**: `examples/local-order-service` plus the phase-5B authorization research fixture
  `research_isolation.py` — a per-tenant authorization layer over the business API, **separate from the default
  startup path** (the ordinary examples are unchanged). The base service has only a coarse global write token and open
  reads, so a tenant is a path segment, not an authenticated principal; the fixture supplies the missing object-level
  authorization. The one-page mechanism note (subject / resource / capability / trust boundary / action / property /
  oracle) is the case's `source` artifact `MECHANISM.md`.
- **Defect/fix variant** (`comparison.before`/`after`, same revision): one configuration flag on the authorization
  component — `authenticate_only` omits the object-level tenant-grant check (defect); `per_tenant` enforces it (fix).
  A project-owned isolated variant, not a fabricated upstream CVE.
- **Model**: one secure specification (`orders-tenant-isolation`, `tenant_isolation` invariant: `forall s,t:
  accessed[s][t] -> grant[s][t]`). Z3 `INVARIANT_VIOLATION` → `NO_WITNESS_WITHIN_BOUND` (the spec admits no violation).
- **Three result classes**, each a real recorded observation replayed against the secure model:
  defect observation → **DEVIATES** (a subject reached another tenant; a real, observed model/program gap), fix
  observation → **CORRESPONDS**, and a cross-tenant write the business layer rejects (no state change) → **UNKNOWN**
  (insufficient evidence). A single passing regression is not a semantic-equivalence proof; an unconfirmed model path
  is not auto-registered as a real defect.

## Phase 6 handoff contract (what a provider model may be given)

Phase 6 runs provider-model inference over an online API, counted apart from the developer (coding) models. It chooses
task inputs **explicitly**; the full research case is never sent to a model.

- **Task material (model-readable)** — the `task_input` artifacts only: for `orders-p2-speed`, the belief model + the
  property + the fixture; for `orders-tenant-isolation`, the secure-spec model + `tenant_isolation` + the mechanism
  note + the grant table. No reference answers, no conformance results, no oracle data.
- **Reference answers (provider-invisible)** — the `reference` artifact (expected correspondence verdicts). Validation
  rejects a reference answer that is also, or is byte-identical to, a task input (`REFERENCE_IN_TASK_INPUT`).
- **Independent scoring interface** — program verification reuses the local regression entry
  (`fal-conformance-result/v1` via `replay_conformance` / `derive_items` + `decide_correspondence` and the case's own
  regression tests). The oracle does not depend on a model scoring its own answer; where the same state machine is used
  to build both a model and an "independent oracle", that shared source is disclosed in the case.
- **Candidate set / feedback policy** — recorded per study in phase 6; a task that supplies existing assistance
  (candidate set, validation feedback) is labelled as such and is **not** read as the model's independent reasoning. A
  "no-assist static analysis" task supplies only the task material above.
- **No free-text execution** — model answers this phase are to-be-verified analysis products only; no component
  translates free text into executable instructions. Domain tasks keep their real purpose, safety property and
  necessary context.

## Phase 6A: provider calls, raw answers and evaluation

6A lets one reviewed task be sent to several provider models, records exactly what came back, and hands the answer to
an independent scorer. The platform, verifiers, evidence and program instances stay local; model inference is online.
The developer (coding) model and the models under test are different identities: every unit records the provider and
the model the response names.

### Protocols (independently versioned, in `formal_lab_contracts.research`; schemas in `contracts/research/`)

| Protocol | Type | Holds |
|---|---|---|
| `fal-research-response/v1` | `ResearchResponse` | `experiment` (study / unit / track / case / task digest / representation / replicate / assistance / sampling id), `call` (provider, api + version, endpoint without credentials, `route`, what answered, model requested / returned, `model_switched`, `model_identity`, provider response id, request id, times, the sampling `params` exactly as sent), `raw` (the provider body as returned or its text, visible text, `finish_reason` as written and its `finish_class`, the explicit refusal field, truncation, tool-call summary, `reasoning` availability), `status` (the call outcome, HTTP status, provider error type and text, every HTTP attempt with sent / confirmed), `cost` (usage known?, input / output / reasoning / cache-read / cache-write tokens as reported, latency, attempts, possibly-billed unconfirmed attempts, prompt and config digests), `task_input_digest`, `reuse_key` |
| `fal-research-study/v1` | `ResearchStudy` | tasks (track, case, representation, the real purpose, input files, assisted inputs, question, answer format / schema, reference file, scorer id + version, bound, split), providers (`ProviderConfig`: provider, api, declared route, endpoint / credential *setting names*, model, params, comparability note), assistance modes, replicates, rubric, primary + secondary metrics, limits (calls, HTTP attempts, output tokens per call / total, fixed network retries), missing policy, pre-registered comparisons |
| `fal-research-evaluation/v1` | `ResearchEvaluation` | the answer axis (`answer_status`), the parsed answer, the behaviour label, refusal status, model-internal and program-correspondence results, per-unit `MetricResult`s, the scorer's explanation, the response / reference / dependency digests and the scoring reuse key — a small static-task record that fabricates no step, world state or execution success |

### Two result axes, stable classes

**Call axis** (`CallOutcome`): `ANSWERED`, `TRUNCATED` (stopped at the output limit; the partial answer is kept),
`CONTENT_REFUSAL` (a refusal or content filter signalled *inside an HTTP success*), `EMPTY_CONTENT`,
`MALFORMED_RESPONSE` (HTTP success, not the provider protocol), `AUTH_ERROR` (401 / 403 — never a content refusal),
`RATE_LIMITED`, `PROVIDER_ERROR` (5xx / overloaded), `REQUEST_REJECTED`, `MODEL_UNAVAILABLE`, `TRANSPORT_ERROR` (never
reached the provider), `UNCERTAIN` (sent, no response: possibly billed), `BUDGET_EXHAUSTED`, `CANCELLED`,
`BLOCKED_NO_CREDENTIAL` (the last three: nothing sent). A model change (`model_switched`) and an unnamed model
(`model_identity = UNKNOWN`) are recorded on every response. Only `ANSWERED / TRUNCATED / CONTENT_REFUSAL /
EMPTY_CONTENT` count as responses the model produced (`MODEL_PRODUCED`).

**Answer axis** (`AnswerStatus`, parsed *after* the raw record is saved): `VALID` (the whole text is the JSON object,
or exactly one fenced JSON block), `INVALID_JSON`, `SCHEMA_VIOLATION`, `TYPE_ERROR`, `EMPTY`, `NO_ANSWER`. A parse
failure stays reviewable; a failed call is never overwritten by a rule fallback (the planners' `RULE_FALLBACK` label is
unchanged and is not a research path). Internal reasoning a provider does not expose is `NOT_EXPOSED`; a provider
thinking block is `SUMMARY_ONLY`, never raw reasoning. An unflagged refusal written as prose is *not* detected by
heuristics in 6A: it appears as `INVALID_FORMAT` with the visible text kept for review (6B scorers may classify it).

### Adapters, routes and credentials (`formal_lab_strategies.model_clients`)

`research_adapter(ProviderConfig, *, setting=read_setting) -> (adapter | None, why)` builds `OpenAIChatAdapter`
(`openai.chat.completions`: content, `message.refusal`, `finish_reason`, usage) or `AnthropicMessagesAdapter`
(`anthropic.messages`, `anthropic-version: 2023-06-01`: text blocks, `stop_reason` incl. `refusal` / `max_tokens`,
thinking as summary, usage incl. cache writes and thinking tokens). `route_of(provider, url)` classifies the endpoint
host: `api.openai.com` / `api.anthropic.com` → `OFFICIAL_NATIVE`, loopback → `LOOPBACK_TEST`, anything else →
`COMPATIBLE_RELAY`; a study whose declared route disagrees with the host is refused. `read_setting(name)` is the only
place a research credential is read and accepts only `FAL_*` names (environment, then the git-ignored `.env`) — a
provider's own variable such as `ANTHROPIC_API_KEY` is never used. No response, prompt, evaluation, report or export
contains a credential (a gateway that echoes one is redacted; the checks scan every written file).

`research_call(adapter, ResearchRequest, *, budget, cancel, network_retries, …) -> ResearchCallResult`: cancellation
and the `ResearchBudget` (calls, HTTP attempts, output tokens) are checked before anything is sent; only connect
failures, lost responses, 429 and 5xx are retried, a fixed number of times; a refusal or any answer is returned as it
came; every attempt is recorded. Model calls, HTTP attempts and possibly-billed unconfirmed requests are counted apart.

### Studies, reuse and resume (`formal_lab_eval.research`)

`load_study` (validates files, scorers, comparisons; rejects a reference that is, or is a copy of, a task input),
`plan_units` (task × provider × assistance × replicate; a mode a task does not define is listed NOT_RUN),
`render` (system prompt with the task's real purpose and format; the inputs; assisted inputs only in ASSISTED),
`cap_params` (enforces the study's per-call output cap, recorded as sent), `run_study`, `score_study`, `build_report`.
Results live in `research/results/<study_id>/`: `ledger.jsonl`, `responses/<unit>--<n>.json` (written before any
parsing), `prompts/<digest>.json` (exactly what was sent), `evaluations/`, `report.json` / `report.md`.

- **Response reuse key** — source case + version, task id + digest (question, format, schema, representation, purpose,
  bound, input-file digests), provider (provider, api + version, route, resolved endpoint, model, params, credential
  *setting name* — on a relay the key selects the account group), assistance mode + assisted-input digests, replicate.
  On resume a unit is reused only if its latest response is one the provider made (`MODEL_PRODUCED` or a malformed
  body) under the same key; anything else (failure, unavailable model, rejected request, cancellation, budget, blocked)
  is called again as a new sample (`sampling_index` + 1) and the earlier record stays in the ledger. Budget counters are
  rebuilt from the ledger, so a resumed study never regains spent calls. A cached response keeps the model identity and
  time it was recorded with; it is never relabelled as a newer model.
- **Scoring reuse key** — response digest + scorer id / version + reference sha256 (the reference pins its own
  dependencies' digests) + rubric + answer format / schema. `score_study` reuses evaluations with the same key and
  never calls a model; `--force` recomputes.

### Scoring interface (6B registers here)

`formal_lab_eval.research_scorers`: a scorer has `scorer_id`, `version` and
`score(parsed, reference, *, repo_root, truncated) -> ScoreOutcome(behavior, model_internal, program_correspondence,
explanation, dependencies)`. Register in-process with `register_scorer(...)`, or ship it in a package under the entry-
point group `formal_lab.research_scorers` (an instance, a class or a list); a task names it by `scorer_id` +
`scorer_version`. The runner owns the call axis and parsing: a scorer only ever receives a parsed answer the model
actually produced, plus its own reference file (never shown to the model). Built-ins:
`orders.deviation-diagnosis@1` (applies the proposed constant revision to the belief model and replays the *recorded
program run* — CORRESPONDS = correct; the expected revision is reported alongside, not used as the criterion) and
`synthetic.shortest-plan@1` (replays the plan on the reference interpreter, compares with the breadth-first shortest
plan; program correspondence is `NOT_APPLICABLE`, never filled in as a pass).

Per-unit metrics (rubric `fal-research-rubric@1`): `correct` (primary; refusals, empty and invalid answers count as
not correct; units without a model-produced response are MISSING — never 0, never 1), `format_valid`, `refused`,
`responded` (NOT_APPLICABLE for units never sent), `program_corresponds` (implementation track only), `output_tokens`
(unknown usage MISSING), `latency_ms`. Aggregates reuse `formal_lab_eval.stats` (Wilson / bootstrap intervals, paired
comparisons with the exact Wilcoxon test only when ≥ 6 non-zero differences).

### Reports and comparisons

`build_report` reports each track separately — never one pooled success rate — with, per condition (provider ·
assistance · representation), the planned denominator, counts of every call outcome and behaviour label, metric
aggregates with n / missing / not-applicable, confirmed tokens, unknown-usage calls, possibly-billed attempts and the
identity (route / identity status / requested → returned). Pre-registered paired comparisons vary one dimension at a
time: provider (key: task, assistance, replicate), assistance (task, provider, replicate), representation (same
reference problem, provider, assistance, replicate). A provider comparison records both parameter sets and their
comparability notes and states that equal parameter names do not mean equal compute and that a fixed seed on a real
API does not reproduce an answer. A comparison with no planned units on one side in a track is marked not applicable.

### Entry points

```bash
uv run --frozen fal research study plan|run|score|report research/studies/<study_id>
uv run --frozen fal research study show research/studies/<study_id> --unit <unit_id>
uv run --frozen fal research study import research/studies/<study_id> --project <project>   # Web: 基准对比 → 研究评测
make research-check ARGS="--group p6a"
```

The platform imports study results read-only (`POST /projects/{pid}/research/studies`, `GET …/research/studies`,
`GET /research/studies/{id}`, `GET /research/studies/{id}/units/{unit_id}`), re-checking every response file against
the digest the ledger recorded. Studies run locally from the host (the checker owns acceptance); they are not a second
scheduler, and Temporal does not run them.

|---|---|---|---|

## Phase 6B: domain criteria, the dual-model experiment and its reading

6B uses the Phase 5 program-grounded cases and the 6A entry points to ask, on a frozen batch: do the models understand
and correctly analyse these formal models; which conclusions hold under independent verification; does the business
framing of the same defined finite problem change answers. The two tracks stay apart and are never pooled.

- **Frozen rubric** `research/rubric/fal-research-rubric-1.json` (version + self-digest, loaded and digest-checked by
  `load_rubric`; the digest is recorded in every report). Six dimensions: formal correctness (deterministic verifier —
  primary metric `correct`), program correspondence (the 5B observation / regression — `program_corresponds`,
  NOT_APPLICABLE for synthetic), assumption & scope expression and observable safety judgment (heuristic signals,
  recorded only — `rubric_signals` on the evaluation, never promoted to a pass), refusal appropriateness (the 6A
  call/answer classification; REFERENCE_UNCERTAIN when the basis is insufficient), usefulness & cost (`output_tokens` /
  `latency_ms` / `format_valid`). No LLM judge and no human review were used, so no dimension is marked expert-reviewed;
  a provider-policy attribution would need a dated public policy basis and is not made.
- **Program-grounded scorer** `orders.isolation-judgment@1`: the answer judges whether tenant isolation held on a
  recorded run of the 5B case; truth comes from the recorded observation (an ungranted access that returned another
  tenant's state is a violation) and program correspondence from the 5B conformance verdict — not from the reference
  answer. Naming a correct violation and stating scope / the risk are recorded as heuristic signals only.
- **Frozen study** `research/studies/p6b-eval/`: 6 conditions × 2 models × 2 replicates = 24 requests, all
  `STATIC_UNASSISTED` (the assisted path is validated in 6A; the MAL hybrid's rule-filtered candidates are an assisted
  condition and never counted as unassisted solving). The real case is `orders-tenant-isolation` with a before/after
  pair (the defect and the fix variants, judged from a factual transcript of the recorded run — the grant table is
  given, the verdict is not). The synthetic tasks are two base problems (a bounded counter, a short route) each in two
  harmless business framings that share one reference (same sample IR digest and shortest answer, so the problems are
  verified-equal and only the framing differs). `load_study` additionally rejects any task whose reference *answer*
  appears in a task input (`ANSWER_LEAK`), proving no answer leakage.
- **Reading of the real batch** (24/24 answered, both tracks): on this frozen engineering batch both models answered
  every unit and were correct on every unit — the program-grounded isolation judgments and the small synthetic plans.
  No representation sensitivity was observed at this difficulty (the two business framings gave the same answers). The
  per-track provider comparison is 0.00 mean difference and is an **engineering reading** only: both models answered
  through a relay (relay-reported identity, K08), the sample is tiny (clustered by case/problem), and the primary
  metric was fixed before the run. GPT-6 Astra used far fewer output tokens than Claude Opus 5.5 (which emitted
  thinking tokens); cost is recorded as reported, not equated. This is a pipeline-and-phenomenon result, not a claim
  of statistical superiority, and nothing here concerns the real-attack-disguise / regulation-evasion experiments,
  which were not run.

## Phase 7: held-out case, closeout and the final status fields

Phase 7 adds a new held-out case to check the method generalises, closes K01–K03 in place, and reports a closeout.

- **Held-out case** `research/cases/ratelimit-token-bucket` (`fal-research-case/v1`): a token-bucket capacity limiter
  — a mechanism different from the order service and tenant isolation — with the `within_capacity` invariant, a
  defect/fix (uncapped vs capped refill) and the scorer `ratelimit.capacity-judgment@1` (program-grounded, from the
  recorded run). Study `research/studies/p7-holdout` (8 requests) is frozen before any model sees it; its reference
  answers come from the program runs. The two Phase-6 synthetic bases are unchanged. A case seen during phase 6 is not
  a fresh held-out set, and a case plus its derived tasks stay in one split group.
- **Gap closure** K01 (receipt binds the concrete target, not a label), K02 (`AttackBudget` enforces
  `max_attack_steps` at the admit point — durable, retry-idempotent, pause/resume-safe), K03 (gate `detail` and the
  three condition states shown). See `known-gaps.md` for the closing evidence.
- **Reproduction** `scripts/p7_reproduce.py` is an automated clean-room **offline** recheck (validate the committed
  cases, read the committed results; no model call, no network); the offline bundle manifest references the research
  data; a re-sampling path needs the user's credentials. Offline recheck is never presented as a new online experiment.

### Final status fields (reported in `docs/handoff/phase7.manifest.json → final_status`)

| field | meaning |
|---|---|
| `engineering_ready` | the local pipeline builds, validates cases offline, runs the dual-model studies and reports, and `make research-check --strict` is complete. It is **not** support for any research hypothesis |
| `experiment_execution_complete` | the dual-model batches were requested, answered and scored with complete denominators. A model answering wrongly, or all models refusing (with requests/responses/scoring present), is still a complete experiment |
| `findings_supported` | what the evidence supports, and at what level (here: **descriptive** — the method and the independent checks work on a second mechanism; no statistical ranking, no verified provider comparison, no general-capability claim) |
| `independent_human_reproduction` | whether a person has independently reproduced the work (PENDING until one does; an agent re-running in a clean directory is only automated reproduction) |
| `original_adviser_scope_complete` | **false** while the original adviser scope's disguised-attack / regulation-evasion experiment is not done; only the adviser can accept an adjusted scope — an agent cannot on their behalf |

Engineering passing does not mean a hypothesis is supported, and models being all wrong does not mean the experiment
is incomplete — the fields are reported independently.
