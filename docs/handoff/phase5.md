## 5A — case, model and evidence foundation (complete)

5A delivers the **generic** research-case and model–program conformance machinery, accepted on the order service and a
harmless finite-state example. Two experiment lines are counted apart from here on: `implementation_conformance`
(software model verification with its real purpose kept) and `synthetic_representation` (fixed, reviewed synthetic
problems — not opened in 5A).

### P5A-01 · case protocol, import validation, provenance display

- **Protocol** `fal-research-case/v1` — `formal_lab_contracts.research.ResearchCase`; JSON Schema at
  `contracts/research/fal-research-case-v1.schema.json` (regenerated by `make contracts`, covered by
  `make contracts-check`). Independently versioned; v1/v2 contracts untouched.
- **Import validation** — `formal_lab_runtime.research.validate_case(files, repo=None)` and the platform import both
  reject failed references, property id/expr-digest mismatch, before/after mix-ups, changed-but-unsealed content and
  stale conformance (codes in protocol.md). Software revision + tree digests are verified where a checkout is at hand.
- **Provenance display** — platform import stores the case document (artifacts in the existing artifact store) and
  links each model version by digest and the recorded observation as an imported run. Shown in the Web (below).
- **Ordinary case** — `research/cases/orders-p2-speed/`, built and validated by `scripts/p5a_orders_case.py`: the order
  service at HEAD under the `deviation` operating condition (station p2 slow); belief model `v1` (nominal) vs revised
  `v2` (`slow[p2]=true`), property `all_completed`. Against one recorded run the belief model **DEVIATES** and the
  revised model **CORRESPONDS**; the service's own regression PASSes.

### P5A-02 · conformance interface, evidence views, shared check entry

- **Protocol** `fal-conformance-result/v1` — three layers kept apart (model conclusion · program regression ·
  correspondence within a declared scope). `replay_conformance` / `replay_items` / `decide_correspondence` in
  `formal_lab_runtime.research`. A passing regression never becomes a semantic-equivalence proof; `UNKNOWN` / `TIMEOUT`
  / `UNSUPPORTED` / `UNCONFIRMED` / `SPURIOUS` are distinct.
- **Evidence views** (existing visual tokens) — ModelWorkbench **研究案例** tab (cases verifying the selected model
  version) and Evidence **对应验证** tab (full provenance for the cases whose recorded observation is the run:
  software revision + trees, models, properties, bounds, assumptions, the three-layer verdicts and the component↔model
  correspondence).
- **Shared check entry** — `scripts/research_check.py` (suite `research`, fixed groups `p5a,p5b,p6a,p6b,p7`) on the
  existing `check_runner`; `make research-check`. The report always carries both `selected_passed` and
  `overall_complete`. p5b–p7 are NO_CHECKS until their executors register checks, so the suite is complete only once
  every required group passes (running one group never marks the whole complete).

### Validation (real results, not hand-written booleans)

`tests/tools/test_research_validate.py` + `test_research_conformance.py` (14 tests): a valid ordinary case, property
mismatch, version mismatch, missing observation, stale evidence, the data-separation rule, offline read, the belief/
revised deviation, three layers apart, and the correspondence-decision branches.
`tests/integration/test_research_platform.py` (2 tests): import → provenance → model-version & run links → export
round-trip (re-validates offline), and a tampered case rejected on import.

## 5B — an implementation-level software safety case (complete)

5B delivers one implementation-level **access-isolation** case, observed on the real order service, with a defect/fix
regression and a model↔program correspondence report. Defensive software verification on local test tenants; the
oracle reads real state, never a self-reported success.

### P5B-01 · the isolation case

- **Finding first.** The base service has only a coarse global write token and open reads — a tenant is a path segment
  and a SQLite file, not an authenticated principal (so "tenant URL ≠ user authentication", as the mentor's question
  anticipated).
- **Research fixture** `examples/local-order-service/.../research_isolation.py`, **separate from the default startup
  path** (the ordinary examples are unchanged): a per-tenant authorization layer over the business API with a
  defect/fix configuration flag — `authenticate_only` omits the object-level tenant-grant check (defect), `per_tenant`
  enforces it (fix). The one-page mechanism note (subject / resource / capability / trust boundary / action / property
  / oracle) is the case's `MECHANISM.md`.
- **Model + property.** One secure specification `orders-tenant-isolation` with the `tenant_isolation` invariant
  (`forall s,t: accessed[s][t] -> grant[s][t]`); Z3 `INVARIANT_VIOLATION` → `NO_WITNESS_WITHIN_BOUND`.
- **Case** `research/cases/orders-tenant-isolation/` built and validated by `scripts/p5b_isolation_case.py`: each key
  action has a real operation + independently-read observation (the owner reads its own state back); a request whose
  outcome is not observable stays UNKNOWN; program-side reference answers are kept out of the task input.

### P5B-02 · defect/fix regression, correspondence, Phase 6 material

- **Three result classes**, each a real recorded observation replayed against the secure model: defect → **DEVIATES**
  (a subject reached another tenant, confirmed by the owner's read), fix → **CORRESPONDS**, and a cross-tenant write the
  business layer rejects (no state change) → **UNKNOWN** (insufficient evidence). Model conclusion, program regression
  and correspondence are kept apart; a passing regression is not a semantic-equivalence proof; the UNKNOWN case is not
  registered as a real defect.
- **Regression** `examples/local-order-service/tests/test_research_isolation.py` (6 tests): unknown principal refused,
  same-tenant access works in both variants, defect allows cross-tenant, fix denies, and the three correspondence
  branches on crafted observations.
- **Phase 6 material** registered in `../research/protocol.md#phase-6-handoff-contract-what-a-provider-model-may-be-given`:
  the `task_input` artifact (model + property + mechanism + grants, no answers) vs the provider-invisible `reference`
  artifact; scoring reuses `fal-conformance-result/v1` and the case's own regression; no component turns free text into
  execution.
